## Pattern Assignments

### `app/telemetry.py` (config/provider-setup, event-driven export)

**No in-repo analog. Reference: RESEARCH.md Pattern 1 — "Dual-exporter OTel setup (console + OTLP, always on)"**, sourced from `opentelemetry.io/docs/languages/python/exporters/` (verified 2026-07-21).

**Core pattern — dual exporters registered on every provider, always on (per D-06, no toggle):**
```python
from opentelemetry.sdk.resources import SERVICE_NAME, Resource
from opentelemetry import trace, metrics
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor, ConsoleSpanExporter
from opentelemetry.exporter.otlp.proto.http.metric_exporter import OTLPMetricExporter
from opentelemetry.sdk.metrics import MeterProvider
from opentelemetry.sdk.metrics.export import PeriodicExportingMetricReader, ConsoleMetricExporter

resource = Resource.create({SERVICE_NAME: "agent-k-rag-service"})

tracer_provider = TracerProvider(resource=resource)
tracer_provider.add_span_processor(BatchSpanProcessor(ConsoleSpanExporter()))
tracer_provider.add_span_processor(
    BatchSpanProcessor(OTLPSpanExporter(endpoint="http://localhost:4318/v1/traces"))
)
trace.set_tracer_provider(tracer_provider)

meter_provider = MeterProvider(
    resource=resource,
    metric_readers=[
        PeriodicExportingMetricReader(ConsoleMetricExporter()),
        PeriodicExportingMetricReader(
            OTLPMetricExporter(endpoint="http://localhost:4318/v1/metrics")
        ),
    ],
)
metrics.set_meter_provider(meter_provider)
```
Logs follow the identical shape (per RESEARCH.md): a `LoggerProvider(resource=resource)` with two processors — one wrapping `ConsoleLogExporter()`, one wrapping `OTLPLogExporter(endpoint="http://localhost:4318/v1/logs")` — attached via a `LoggingHandler` on the root Python logger.

**Notes for the planner:**
- All three signals (traces, metrics, logs) share the same `Resource` object with `SERVICE_NAME` — this is the single source-of-truth service name that CLAUDE.md's "Conventions" section will eventually reference.
- OTLP endpoint must use HTTP/protobuf on port 4318 (D-07) — never gRPC (4317), per CLAUDE.md's "What NOT to Use" table.
- This module should expose a single `setup_telemetry()` (or similar) function `app/main.py` calls at startup, so Phase 2 can import and extend it without re-wiring providers.

### `app/main.py` (controller/config, request-response)

**No in-repo analog. Reference: RESEARCH.md Pattern 2 — "FastAPI + logging instrumentation (one-liners, order matters)"**, sourced from `opentelemetry-python-contrib.readthedocs.io` (verified 2026-07-21).

**Core pattern — instrument only AFTER routes are registered:**
```python
import fastapi
from opentelemetry.instrumentation.fastapi import FastAPIInstrumentor
from opentelemetry.instrumentation.logging import LoggingInstrumentor

app = fastapi.FastAPI()

@app.get("/healthz")
async def healthz():
    return {"status": "ok"}

# Must come AFTER route registration — instrumenting before routes exist
# means those routes are never wrapped.
FastAPIInstrumentor.instrument_app(app)

LoggingInstrumentor().instrument(set_logging_format=True)
# Injects %(otelTraceID)s / %(otelSpanID)s / %(otelServiceName)s into every
# stdlib logging record made while a span is active.
```

**Anti-pattern flagged in RESEARCH.md:** Calling `FastAPIInstrumentor.instrument_app(app)` before routes are registered silently produces incomplete tracing — routes added later are never wrapped. The planner must sequence: (1) create `app = FastAPI()`, (2) register all routes (`/healthz` in this phase), (3) call `setup_telemetry()` from `app/telemetry.py`, (4) call `FastAPIInstrumentor.instrument_app(app)`, (5) call `LoggingInstrumentor().instrument(...)`.

**Data flow note:** This is a request-response controller file (per D-04, a real reusable scaffold, not disposable) — Phase 2 extends it with the `/ask` route rather than replacing it. Keep OTel setup imports/calls isolated so Phase 2 can add routes above the instrumentation call without restructuring.

### `casting.yaml` (config, batch/declarative)

**No in-repo analog. Reference: RESEARCH.md "Code Examples" — Minimal `casting.yaml` (Docker Compose mode)**, sourced from `github.com/SigNoz/foundry/blob/main/docs/getting-started.md` (verified 2026-07-21).

```yaml
apiVersion: v1alpha1
metadata:
  name: signoz
spec:
  deployment:
    mode: docker
    flavor: compose
```

**Core sequencing pattern (RESEARCH.md Pattern 3 — "Foundry gauge → forge → cast, decoupled for debuggability"):**
```bash
foundryctl gauge -f casting.yaml         # validate prerequisites (Docker, Compose v2)
foundryctl forge -f casting.yaml -p ./pours   # generate pours/ + casting.yaml.lock
foundryctl cast -f casting.yaml          # full pipeline: gauge + forge + deploy

# D-02 fallback (per Pitfall 1 — legacy docker-compose.yaml no longer exists upstream):
# if cast hangs/fails but forge succeeded, deploy manually to isolate the failure:
docker compose -f pours/deployment/compose.yaml up -d
docker compose -f pours/deployment/compose.yaml logs -f signoz-signoz-0
```

**Critical constraint (Pitfall 1 in RESEARCH.md):** Do NOT write a fallback runbook step referencing cloning `SigNoz/signoz`'s plain `docker-compose.yaml` — it was removed upstream as of v0.130.0. The correct fallback is `forge` (generate only) + manual `docker compose up -d` against `pours/deployment/compose.yaml`.

**`casting.yaml.lock`:** Auto-generated by `forge`/`cast` — never hand-write this file. Both `casting.yaml` and `casting.yaml.lock` must be explicitly `git add`-ed and confirmed tracked (Pitfall 4) — do not let habitual gitignore rules for "lock-looking" files suppress it. `pours/` itself should be gitignored (regenerable, may contain machine-specific paths).

### `scripts/time-foundry-cast.sh` (utility, batch)

**No in-repo analog. Reference: RESEARCH.md "Code Examples" — Rebuild-time wrapper script (bash variant, D-08)**, this agent's synthesis per RESEARCH.md (not from an external doc — flagged `[ASSUMED]` there, straightforward shell timing).

```bash
#!/usr/bin/env bash
set -euo pipefail
START=$(date +%s)
foundryctl cast -f casting.yaml
END=$(date +%s)
DURATION=$((END - START))
TIMESTAMP=$(date -u +"%Y-%m-%dT%H:%M:%SZ")
printf "| %s | %ds |\n" "$TIMESTAMP" "$DURATION" >> TELEMETRY-REBUILD-LOG.md
echo "Foundry cast completed in ${DURATION}s — logged to TELEMETRY-REBUILD-LOG.md"
```

**Notes for planner:**
- CONTEXT.md D-08 leaves shell-vs-Python as Claude's discretion; this bash variant is the one RESEARCH.md provides concretely — use it unless the planner has a strong reason to prefer Python (e.g., team more comfortable there).
- `TELEMETRY-REBUILD-LOG.md` must be initialized with a markdown table header (`| Timestamp (UTC) | Duration |` / `|---|---|`) before the first script run so appends produce a clean table.
- The timer should start only after prerequisites are confirmed (arguably exclude the one-time `foundryctl` binary install itself) — RESEARCH.md's Open Question #1 flags this as the boundary decision for what counts toward the 15-minute TELE-02 budget.
